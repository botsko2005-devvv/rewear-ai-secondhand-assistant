# Архітектура системи

## Загальна схема взаємодії
Система побудована за клієнт-серверною архітектурою з розподілом відповідальності: мобільний застосунок відповідає за введення даних, первинну валідацію форми, відображення станів UI та локальне збереження історії, а валідація контракту, бізнес-логіка й AI-обробка виконуються на backend.

```text
[Mobile: Android (Kotlin + Jetpack Compose + Room Database)]
       │  HTTP POST /api/v1/listing (JSON)
       ▼
[Backend: FastAPI + Pydantic (Python)]
       │  provider.generate(description, condition, size)
       ▼
[AI Component: MockProvider (правила за ключовими словами)]
```

## Стани мобільного інтерфейсу (`UiState`)
`ListingViewModel` керує станом екрана через `sealed class UiState`:
1. `Idle` — початковий стан до натискання кнопки генерації.
2. `Loading` — активний HTTP-запит (відображається `CircularProgressIndicator`, кнопка блокується).
3. `Success(listing)` — отримано успішну відповідь (`status == "ok"`), відображається картка з категорією, ціною, заголовком, описом і кнопкою копіювання.
4. `NoResult(hint)` — отримано `status == "low_confidence"`, відображається порада уточнити опис.
5. `Error(message)` — помилка валідації, мережі, таймауту або парсингу JSON із кнопкою «Повторити».

## Шар локального збереження (Room Database)
Для реалізації локальної історії (ЛР4) використано **Room Database** (версія 2.7.1) та кодогенерацію **KSP** (`2.2.10-2.0.2`):
- **`HistoryEntity`**: таблиця `listing_history` містить унікальний `id` (autoGenerate), `createdAt` (формат "yyyy-MM-dd HH:mm"), `timestamp`, `status` ("готово"), вхідні параметри (`description`, `condition`, `size`, `platform`) та результати AI-генерації (`category`, `title`, `resultDescription`, `priceMin`, `priceMax`, `currency`, `confidence`).
- **`HistoryDao`**: надає асинхронні методи (`suspend`) та реактивний потік `Flow<List<HistoryEntity>>` з сортуванням за `timestamp DESC`.
- **`AppDatabase`**: абстрактний клас `RoomDatabase` із singleton-ініціалізацією (`rewear_database`).
- **`HistoryRepository`**: інкапсулює роботу з DAO для `ListingViewModel`.

**Правило збереження в історію:** Запис зберігається в базу даних **ТІЛЬКИ** за умови успішної відповіді сервера (`response.isSuccessful`) та статусу `body.status == "ok"`. Помилки мережі, винятки, сервери з помилками та відповіді зі статусом `low_confidence` свідомо не зберігаються в історії.

## Локальне мережеве підключення
Backend запускається на `0.0.0.0:8000`. Для з'єднання емулятора Android із локальним сервером використовується прокидання порту `adb reverse tcp:8000 tcp:8000` та `BASE_URL = "http://127.0.0.1:8000/"`.

## Лабораторна робота №7: Підсумкова інтеграція, архітектура та стани UI

### 1. Опис фінального сценарію
Фінальний сценарій інтеграції об'єднує всі розроблені компоненти мобільного AI-помічника продавця секонд-хенду (ReWear AI):
1. **Користувацький ввід:** Користувач вводить опис речі, обирає стан (`new`, `excellent`, `good`, `fair`), розмір та маркетплейс публікації (`OLX`, `eBay`, `Grailed`).
2. **Мережевий запит:** Мобільний клієнт (Kotlin, Jetpack Compose) формує POST-запит до FastAPI backend через Retrofit із таймаутом 10 с.
3. **Обробка на сервері:** Запит обробляється шаруватим бекендом з ін'єкцією залежностей (`FastAPI Depends`), детермінованим або реальним провайдером (`MockListingProvider` / `RealListingProvider`), з урахуванням сегмента бренду (`brand_tier`), дефектів та розрахунку ціни у валюті (`UAH`).
4. **Збереження історії:** Успішні відповіді зі статусом `ok` автоматично зберігаються на пристрої в базі даних Room через `HistoryRepository`.
5. **Відображення та взаємодія:** Користувач бачить фінальну картку оголошення з можливістю копіювання в один клік, перегляду деталей у вкладці історії або взаємодії з підказками (`suggestions`) у разі низької впевненості ШІ.

### 2. Критерії роботи системи (Operational Criteria)
1. **Швидкодія та детермінованість:** Час відповіді mock-провайдера становить менше 500 мс, забезпечуючи миттєву генерацію на мобільному пристрої.
2. **Надійність локального сховища:** Успішні генерації гарантовано зберігаються в SQLite (Room Database) з можливістю автономного перегляду історії без підключення до мережі.
3. **Стійкість до помилок та відновлення:** Грамотне перехоплення винятків (JSON парсинг, таймаути, помилки мережі) повертає чіткі стани UI без крашів застосунку.
4. **Підтримка платформ і адаптивність:** Коректне форматування заголовків, описів та тегів під специфіку кожного маркетплейсу (`OLX`, `eBay`, `Grailed`).
5. **Зворотна сумісність контракту:** Усі нові поля API є опціональними або мають значення за замовчуванням, що гарантує роботу клієнта зі старішими версіями сервера.

### 3. Поведінка всіх станів UI (включно з фоном та повторним запитом)
- **`Idle` (Початковий стан):** Поля введення чисті, кнопка генерації активна, історія завантажена з бази даних.
- **`Loading` (Завантаження):** Відображається індикатор `CircularProgressIndicator`, поля введення блокуються для запобігання дублюванню запитів.
- **`Success` (Успіх):** Відображається картка з результатами (категорія, ціна, заголовок, опис, кнопка копіювання в буфер обміну). Запис автоматично додається до Room Database.
- **`NoResult` / `LowConfidence` (Низька впевненість):** Повертається порада (`hint`) та інтерактивні чіпи (`suggestions`), натискання на які додає рекомендації до опису в один клік.
- **`Error` (Помилка мережі / сервера / JSON):** Відображається зрозуміле повідомлення про помилку (без технічного `stack trace`) та кнопка «Повторити».
- **Повернення з фону (Process Death / Activity Recreation):**
  - Якщо застосунок був вивантажений системою з оперативної пам'яті під час перегляду історії чи після генерації, при повторному відкритті стан ViewModel ініціалізується заново, а локальна історія миттєво зчитується з Room Database (`Flow<List<HistoryEntity>>`), відновлюючи попередні успішні результати.
- **Повторний запит без перезапуску (Retry без перезапуску):**
  - При виникненні мережевої помилки (наприклад, сервер був недоступний / `502` / `504`) користувач залишається на екрані генерації зі збереженими вхідними даними. Після відновлення роботи сервера користувач натискає кнопку «Повторити», і запит виконується успішно без необхідності перезапускати застосунок.
